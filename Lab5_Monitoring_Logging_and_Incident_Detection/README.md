# Task 2: Centralize Logs (Ship to CloudWatch)
LocalStack was started, a log group (/ccse/app) and log stream (auth) were created, and the local log lines were pushed line-by-line to CloudWatch Logs.

Command Summary:
```
docker run -d --name localstack -p 4566:4566 localstack/localstack

EP='--endpoint-url=http://localhost:4566'
aws $EP logs create-log-group --log-group-name /ccse/app
aws $EP logs create-log-stream --log-group-name /ccse/app --log-stream-name auth

TS=$(date +%s000)
while IFS= read -r line; do
  aws $EP logs put-log-events --log-group-name /ccse/app --log-stream-name auth \
    --log-events timestamp=$TS,message="$line" >/dev/null
  TS=$((TS+1000))
done < auth.log

aws $EP logs get-log-events --log-group-name /ccse/app --log-stream-name auth \
  --query 'events[].message' --output text
```
Result:

The get-log-events command read back all log lines from LocalStack CloudWatch, confirming centralized log collection.

# Task 4: Tamper-Proof (Hash-Chained) Logs
A sequential hash chain was generated by appending the hash of each log entry to the previous entry's hash. A file tampering test was then conducted to prove that modifying log content breaks the hash chain.

Command Summary:
```
# Generate the original hash chain
PREV=0
while IFS= read -r line; do
  PREV=$(printf '%s%s' "$PREV" "$line" | sha256sum | cut -d' ' -f1)
  printf '%s | %s\n' "$line" "$PREV"
done < auth.log > auth.chain

cat auth.chain

# Tamper test: modify export size from 500MB to 5MB
sed 's/500MB/5MB/' auth.log > auth.tampered

PREV=0
while IFS= read -r line; do
  PREV=$(printf '%s%s' "$PREV" "$line" | sha256sum | cut -d' ' -f1)
done < auth.tampered

echo "Tampered final hash: $PREV"
echo "Original final hash: $(tail -n1 auth.chain | cut -d'|' -f2 | tr -d ' ')"
```
Result:

The final hash computed from auth.tampered did not match the original final hash in auth.chain. This proves that any unauthorized modification immediately breaks the chain.

# Task 5: Detect the Incident (Correlation)
A detection rule was executed to correlate events. Checking if a single IP address had 3 or more failed logins, followed by a successful login, and followed by a data export.

Command Summary:
```
IP="203.0.113.9"
FAILS=$(grep -c "LOGIN FAIL.*$IP" auth.log)
SUCCESS=$(grep -c "LOGIN OK.*$IP" auth.log)
EXPORT=$(grep -c "EXPORT DATA.*$IP" auth.log)

echo "IP=$IP fails=$FAILS success=$SUCCESS export=$EXPORT"

if [ "$FAILS" -ge 3 ] && [ "$SUCCESS" -ge 1 ] && [ "$EXPORT" -ge 1 ]; then
  echo 'ALERT: probable brute-force -> compromise -> data exfiltration'
fi
```
Result:

The script printed ALERT: probable brute-force -> compromise -> data exfiltration, confirming successful incident detection via event correlation.

# Task 6: Incident Response
Incident response was performed by containing the attacker's IP address using iptables, creating a copy of the log file for evidence, and calculating its SHA-256 digest.

Command Summary:
```
# Containment: block the offending IP address
docker run --rm --cap-add=NET_ADMIN alpine sh -c "apk add -q iptables && iptables -A INPUT -s 203.0.113.9 -j DROP && iptables -L INPUT -n | tail -2"

# Evidence Collection: create a timestamped copy and generate SHA-256 hash
cp auth.log "evidence_$(date +%Y%m%d).log"
sha256sum evidence_*.log > evidence.sha256
cat evidence.sha256
```
Result:

The iptables rule successfully dropped incoming traffic from 203.0.113.9, and the evidence file hash was generated and saved.

# Incident Report
1. Detection

At timestamp 2025-03-01T09:01:40, an alert was triggered due to an anomalous pattern originating from IP address 203.0.113.9. The alert was identified using a automated log correlation script monitoring application telemetry.

2. Analysis

Log analysis showed 4 consecutive failed login attempts targeting the admin account from IP 203.0.113.9 within 8 seconds. At 09:01:22, a successful authentication occurred from the same IP, followed by a 500MB data export at 09:01:40. This sequence indicates a successful brute-force attack followed by data exfiltration.

3. Containment

Immediate containment was executed by applying an iptables drop rule (iptables -A INPUT -s 203.0.113.9 -j DROP) to block all incoming network traffic from the attacker's IP address.

4. Evidence & Integrity

The raw authentication log was copied to an isolated file (evidence_20250301.log). A SHA-256 fingerprint was computed and stored in evidence.sha256 to maintain cryptographic chain of custody and prevent evidence tampering.

5. Lesson Learned

Relying on individual log lines is insufficient for threat detection. Automated SIEM correlation rules and real-time alerts must be configured to catch brute-force attempts before an account is compromised and data is exported.

# Short-Answer Questions
Q1. What is the difference between a log and an event? Give an example of each from this lab.

- Log: A static, recorded record of an activity saved to a file. Example: The raw text entry 2025-03-01T09:00:01 LOGIN OK user=ahmad stored inside auth.log.

- Event: A real-time notification or alert triggered when specific criteria are met. Example: The automated system alert ALERT: probable brute-force -> compromise -> data exfiltration generated by the script.

Q2. Why must audit logs be tamper-proof, and how does a hash chain achieve this?

Audit logs must be tamper-proof so attackers cannot erase their actions or cover their tracks after gaining access. A hash chain achieves this by incorporating the previous entry's hash into the calculation of the current entry's hash. If an attacker alters any historical line, every subsequent hash changes, exposing the modification.

Q3. How did correlation detect an incident that no single log line revealed?

No single log line was illegal by itself. Failed logins happen, successful logins are normal, and data exports are standard features. However, correlating the timeline revealed a brute-force pattern leading directly to account access and a large data transfer from the exact same IP address.

Q4. List the incident-response steps you performed and the goal of each.

1. Detection: Identified the attack using automated event correlation rules.

2. Containment: Blocked the attacker's IP address with iptables to stop active data exfiltration.

3. Evidence Collection: Created a timestamped copy of log files and recorded its SHA-256 hash to secure digital evidence.

4. Documentation: Wrote a structured incident report to record what happened and note lessons learned.

Q5. How do the same logs serve both security monitoring and compliance evidence?

For security monitoring, logs provide real-time visibility to detect attacks as they happen. For compliance, logs serve as immutable audit trails that prove to auditors that security controls are active, access is tracked, and data integrity is maintained.
